# Намір і критерії
  - Намір: Визначити сутності й атрибути та побудувати узгоджену ERD для системи управління навчальним процесом університету (факультети, кафедри, спеціальності, групи, студенти, викладачі, курси та зарахування);
  - Критерії готовності: усі сутності, атрибути та обмеження з spec.md відображені в ERD, враховано UNIQUE, CHECK, типи даних, PK (number) та FK збігаються між spec.md та erd.md, кардинальності (1:1, 1:N) відповідають бізнес-логіці вишу, зв'язок N:M (студент–курс) розбито через асоціативну сутність для зберігання оцінок, відсутнє дублювання даних;

# Топ-3 розбіжності, виправлення

*1)Відсутність складеного обмеження унікальності*
  - Розбіжність: у початковій ER-моделі сутність ENROLLMENT містила лише первинний ключ enrollment_id. Це створювало можливість дублювання даних, коли один і той самий студент міг бути зареєстрований на один і той самий курс кілька разів у межах одного семестру;
  - Виправлення: у spec.md додано бізнес-обмеження UNIQUE(student_id, course_id) для сутності ENROLLMENT, щоб гарантувати унікальність пари "студент–курс";
  - Коміт: https://github.com/overdimension/KPI2-labs/commit/278723e327cf337935d1937931235822c38f3092;
  - Чому: без цього обмеження база даних дозволяє створювати дублікати записів зарахування, що призводить до аномалій під час підрахунку підсумкових оцінок та ECTS-кредитів;
  
*2)Відсутність обмеження діапазону балів для атрибута grade*
  - Розбіжність: у специфікації зазначалося, що підсумкова оцінка складає від 0 до 100 балів, проте в ER-моделі атрибут був описаний просто як number grade без будь-яких валідаційних правил;
  - Виправлення: у spec.md явно вказано правило діапазону grade: number "0..100";
  - Коміт: https://github.com/overdimension/KPI2-labs/commit/02ae232deb879b24f89135dc448467acc49dec41;
  - Чому: відсутність обмеження створює ризик внесення некоректних або помилкових даних (наприклад, від'ємних балів або значень понад 100), що порушує цілісність системи оцінювання;
  
*3)Відсутність дати закінчення навчання / випуску у сутності STUDENT* 
  - Розбіжність: сутність STUDENT містить дату вступу (admission_date), але не має атрибута для фіксації дати завершення навчання або відрахування;
  - Виправлення: у spec.md додано опціональне поле graduation_date (date) для сутності STUDENT;
  - Коміт: https://github.com/overdimension/KPI2-labs/commit/dd956aec56b51bc1553b9230f1cd764fbe805d48;
  - Чому: без дати завершення навчання система не здатна коректно визначати тривалість навчання студента та формувати архівні відомості й додатки до дипломів випускників;

# Ключове рішення(ADR)
  - Проблема була в тому, що правила роботи системи вимагають зв'язку багато-до-багатьох між студентами та курсами, адже один студент вивчає багато курсів, а один курс вивчають багато студентів.
  - Альтернатива вирішення 1 — course_id у таблиці STUDENT (1:N). Найпростіша схема, але вона обмежує студента можливістю вивчати тільки один курс за раз. Для реального освітнього процесу це неприпустимо, оскільки втрачається історія вивчення інших дисциплін;
  - Альтернатива вирішення 2 — Окрема таблиця ENROLLMENT. Створює асоціативну сутність для зв'язку «багато до багатьох» і дозволяє прикріпити до кожного випадку вивчення курсу специфічні дані (оцінку grade, статус складання тощо);
  - Рішення: Обрано Альтернативу 2 із розбиттям через асоціативну сутність: STUDENT ||--o{ ENROLLMENT }o--|| COURSE;

# Перевірка

  - За допомогою аналітичного промпту порівняно сутності, їхні атрибути, типи даних та зв'язки зі spec.md із блоками Mermaid ERD.
  - Ключові зміни від початкового задуму:
    - Впроваджено асоціативну сутність ENROLLMENT для зв'язку N:M між студентами та курсами
    - Додано складене обмеження унікальності UNIQUE(student_id, course_id), яке унеможливлює повторну реєстрацію на той самий курс
    - Встановлено правила перевірки балів CHECK (grade >= 0 AND grade <= 100)
    - Унифіковано всі первинні ключі — їх зведено до єдиного типу number
